# ADR-0017: Tenant suspension and deletion — grace deadline column, tombstone-on-delete, deferred object storage, synchronous CLI until River

**Status:** Accepted · **Date:** 2026-08-21 · **Requirements:** FR-TEN-04/05, SPEC-01 §8, C-1/ADR-0001, C-3, C-4/ADR-0012, ADR-0003, ADR-0005, ADR-0016, SPEC-09

## Context
STORY-02.4 implements the rest of the tenant lifecycle: suspension (reads only; end-user query/ingest refused, admins can still read — FR-TEN-04), and deletion with a configurable grace period during which a platform admin can cancel, after which the drop is irreversible (FR-TEN-05, SPEC-01 §8). The resolver already applies the status rules (ADR-0003, SPEC-01 §3) and invalidates its cache within ~1s via the `tenant_changed` LISTEN/NOTIFY trigger (STORY-02.1); this story provides the state transitions that drive them and the teardown that drops the tenant's database and role.

Open sub-decisions:
1. **Where the grace deadline lives** so the drop can be gated on it and a scheduler can find eligible tenants.
2. **What "delete" leaves behind.** SPEC-01 §8 says drop the database and role and cascade-delete the control-plane rows; but a fully cascaded `DELETE FROM tenants` also removes the audit history for that tenant.
3. **Object-storage prefix removal** when no S3/MinIO client exists in the repo yet.
4. **Async job vs. synchronous call**, mirroring the provisioning decision (ADR-0016): River (ADR-0005) is EPIC-09 and not yet present.
5. **How cancellation restores the right state** (a suspended tenant scheduled for deletion should come back suspended, not active).

## Decision
- **A `Lifecycle` service in `internal/provision`** (not `internal/tenant`, which stays the data-plane-only path per ADR-0003) holds `Suspend`, `Resume`, `ScheduleDelete`, `CancelDelete`, `RunDelete`. It reuses the provisioner's privileged-connection pattern: the status writes are control-plane, and `DROP DATABASE`/`DROP ROLE` are superuser-only DDL. The teardown SQL reuses the same validate-then-quote identifier guard as provisioning (`quoteIdent`, fail closed), so a crafted name cannot break out of the non-parameterisable DDL.
- **A new nullable `tenants.delete_after timestamptz` column** (control migration `00003`, mirrored into `schemas/control_plane.sql` under the drift guard) records the grace deadline. It is set to `now() + grace` (default 7 days) on `ScheduleDelete`, cleared on `CancelDelete`, and gates `RunDelete`, which refuses to drop before it. A partial index (`where status = 'deleting'`) lets the future scheduler cheaply find tenants past their window. Storing the deadline on the tenant row (rather than only in a River job) keeps the grace state authoritative in the control plane and independent of the queue.
- **An explicit status state machine** (`transitions.go`): active↔suspended, active/suspended→deleting, deleting→(active|suspended) for cancellation, deleting→deleted for the final drop. Everything else — including no-ops and any transition out of `deleted` — is rejected (`errIllegalTransition`), so a caller cannot resurrect a deleted tenant or skip the grace period. Provisioning→active is deliberately absent: that is the provisioner's job (ADR-0016), not this service's.
- **Tombstone, not full cascade.** `RunDelete` explicitly deletes the tenant's child rows (`tenant_databases`, `tenant_members`, `api_keys`, `sources`, `jobs`, `usage_daily`) and sets the `tenants` row to `deleted` with `deleted_at`, rather than `DELETE FROM tenants` (which would cascade everything, including audit rows whose `tenant_id` FK is `ON DELETE SET NULL`). This satisfies "no rows remain" for tenant content/registry while retaining the tenants tombstone and its audit trail (FR-ADM-05 history survives a deletion). The required verification test asserts zero rows in every child table for the deleted tenant.
- **Ordering:** drop the database first, then the role (so the role owns nothing and `DROP ROLE` cannot fail on dependent objects), then the registry deletes. `DROP DATABASE ... WITH (FORCE)` terminates any residual sessions (a suspended tenant's evicted pool, a stray admin connection). Every drop is `IF EXISTS`, so a re-run after a partial teardown completes cleanly — the precondition for wiring this as a retried River `delete_tenant` job later with no handler changes.
- **Object-storage removal is deferred, not silently skipped.** No S3/MinIO client exists in the repo yet (only the AWS KMS SDK, for crypto). `Lifecycle` depends on a small `ObjectPrefixDeleter` behaviour; when nil it records `ObjectStoreDeferred` on the result and in the `tenant.delete.complete` audit event, and the CLI prints a notice. EPIC-06 (object storage / upload connector) wires the concrete client. This avoids inventing a large storage abstraction before its owning epic, per the story's guidance, while keeping the seam and an auditable record that the step is outstanding.
- **Synchronous `ragctl tenant …` now; async enqueue deferred to EPIC-09.** As with enroll (ADR-0016), the commands call the idempotent handler directly. `ragctl tenant delete --run` honours the grace deadline in-handler. When River lands, `delete_tenant` (already in the `job_kind` enum, SPEC-08 §1) will schedule the drop for `delete_after` and call this same `RunDelete`.
- **Cancellation restores the prior status.** `ScheduleDelete` stashes the pre-delete status in `settings.delete_prev_status`; `CancelDelete` reads it and restores `active`/`suspended` (defaulting to `active` if absent/invalid) and removes the key. No extra column is needed.
- **Audit on every transition** (C-3, control-plane only): `tenant.suspend`, `tenant.resume`, `tenant.delete.schedule`, `tenant.delete.cancel`, `tenant.delete.complete`, carrying non-secret metadata only.

## Consequences
- The grace window is enforced by the control plane regardless of whether a queue is present; `RunDelete` before the deadline is refused (unit-covered by the transition/grace helpers and e2e-covered end to end).
- Deletion is idempotent and retry-safe, so it drops straight into a River job in EPIC-09.
- Audit history for deleted tenants survives (tombstone), at the cost of one retained `tenants` row per deleted tenant; garbage-collecting tombstones, if ever wanted, is a separate future decision.
- Object-storage cleanup is outstanding and explicitly tracked (result flag + audit + CLI notice) until EPIC-06; no bytes are silently orphaned without a record.
- New spec text: SPEC-01 §8 is updated in this change to describe the `delete_after` deadline, the tombstone semantics, the ordering, and the deferred object-storage step (NFR-MNT-04: ADR + spec updated with the code).
- The DB orchestration is covered by the required e2e against the real stack (suspend→read-only + admin-read, schedule→unavailable + deadline recorded, run-before-grace refused, cancel→restored + no drop, run-past-grace→dropped + no rows remain); the pure helpers (teardown SQL builders, transition validation, grace math) are unit-tested.
