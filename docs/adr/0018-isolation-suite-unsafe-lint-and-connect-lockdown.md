# ADR-0018: Isolation test suite — forbidigo-enforced Unsafe() ban and PUBLIC-CONNECT lockdown per tenant database

**Status:** Accepted · **Date:** 2026-08-22 · **Requirements:** NFR-SEC-01, SPEC-01 §6/§9, FR-ACC-03, C-1/ADR-0001, ADR-0003, ADR-0016

## Context
STORY-02.6 (the last of EPIC-02) delivers the isolation test suite SPEC-01 §9 requires: enrol two tenants and prove that credentials/identity for tenant A can never read or write tenant B's data, including by guessing IDs. It also carries the backlog task "lint rule forbidding `Unsafe()` outside allowed packages".

Two design questions had to be settled:

1. **How to enforce, in CI, that `tenant.DB.Unsafe()` (the raw `*pgxpool` escape hatch, ADR-0003) is not called outside the privileged provisioning/migration packages.** `Unsafe()` is a method call, not an import, so `depguard` (import-based) does not apply. Options: a custom `go vet`-style analyzer, an AST-grepping test, or a golangci-lint text/AST rule.

2. **Whether the current per-tenant database provisioning actually satisfies NFR-SEC-01's "no query path SHALL be able to address another tenant's database".** Writing the isolation suite surfaced the answer: it did not, fully. `CREATE DATABASE ... OWNER role` (ADR-0016) leaves Postgres's default `CONNECT` grant to `PUBLIC` in place, so tenant A's least-privilege role can open a session against tenant B's database and enumerate its catalog (table/column names), even though table-level ownership keeps the row data itself unreadable and PG16 already revokes `CREATE` on `public` from `PUBLIC`. Connecting at all, and reading catalog metadata, is a query path addressing another tenant's database — contrary to the connection-level boundary NFR-SEC-01 mandates.

## Decision
- **Enforce the `Unsafe()` ban with golangci-lint `forbidigo`.** The linter is already wired into `mise run lint` and thus CI (ADR-0014), so no new tool, analyzer binary, or bespoke test is introduced. The rule forbids the selector `\.Unsafe$` (forbidigo matches the textual selector name, e.g. `db.Unsafe`; anchoring on `.Unsafe$` matches the method precisely and leaves stdlib `unsafe.Pointer` and any package literally named `unsafe` untouched). `analyze-types: false` avoids cross-package type resolution — the method name is bespoke in this codebase, so the textual match is exact enough. The privileged packages keep their access via `issues.exclude-rules` scoped to `internal/provision/` and `internal/migrate/` — the two packages that legitimately reach the raw pool (verified against the current tree). Any other package calling `Unsafe()` fails `mise run lint` in CI. Proven both ways during development: a temporary offending call outside the allowlist is flagged (RED), and a temporary call inside `internal/provision` is not.
- **Close the connection-level boundary at provision time.** `createRoleAndDatabase` now runs, after `CREATE DATABASE`, an idempotent lockdown (`lockdownDatabaseSQL`): `REVOKE CONNECT ON DATABASE <db> FROM PUBLIC` followed by `GRANT CONNECT ON DATABASE <db> TO <owner>`. After this, only the owning tenant role (and the superuser used for provisioning/migration) can open a session against the database; another tenant's role is rejected by Postgres at connect time, so it cannot address the database at all — not its rows, not its catalog. The statements are idempotent, so provisioning retries (ADR-0016) remain safe, and re-running enrol also repairs any database created before this lockdown existed. Identifiers reuse the existing validate-then-quote guard (`quoteIdent`, fail closed).
- **Assert isolation at the layer that exists today (resolver + `tenant.DB`).** The public HTTP router is STORY-04.1 (EPIC-04) and does not exist yet, so the suite proves, against the real stack: (a) resolving A's ID yields A's data and only A's, and B's ID yields B's — identity comes from the registry, never a client parameter (FR-ACC-03); (b) A's resolved connection cannot read B's rows; (c) A's credentials against B's database are rejected by Postgres, with a control proving A still reaches its own database (NFR-SEC-01). The two-tenant fixture (`enrollIsolationTenant`, `openTenantByID`) is built so the router-driven cross-tenant endpoint matrix (A's credentials against B's IDs over every tenant-scoped route, asserting 404/403) can plug in when EPIC-04 lands; only the HTTP driver is deferred.

## Consequences
- The ADR-0003 rule is now machine-enforced on every PR: no application package can bypass the resolver's read-only/isolation guarantees via the raw pool without failing CI.
- Cross-tenant database access is denied at the Postgres connection level, satisfying NFR-SEC-01 in defence-in-depth with the existing table ownership — a resolver bug that handed out a wrong connection string could still not authenticate into the wrong database.
- One redundant `Unsafe()` call in the STORY-02.1 resolver e2e (a pool-identity check already covered by the internal `TestPoolCacheLazyCreateAndReuse` unit test) was replaced with a black-box write-then-read reuse assertion, so the e2e no longer needs the escape hatch.
- New/updated spec text (NFR-MNT-04: spec updated with the code): SPEC-01 §6 gains the CONNECT lockdown step; SPEC-01 §9 records the layer the suite asserts at today and the EPIC-04 follow-up; SPEC-09 §1 notes the PUBLIC-CONNECT revoke.
- The lockdown is unit-tested (`lockdownDatabaseSQL` — revoke/grant/quoting/fail-closed) and end-to-end-tested (the isolation suite proves A cannot connect to B's database, and enrol/lifecycle/move e2e prove the owner still can).
